## 1. What It Is

`train_agentic_rl_async.py` is MiniMind's **asynchronous Agentic RL** trainer for multi-turn tool-use tasks.

It inherits the core ingredients already present in `train_agent.py`:

- multi-turn tool-augmented rollout
- delayed rewards from `gt`, format quality, and tool outcomes
- decoupling between the learner and the rollout engine

But it pushes the training loop from:

```text
collect a full batch of trajectories -> update once
```

to:

```text
produce rollouts continuously in the background -> consume fresh trajectories continuously -> update with version-aware near-on-policy correction
```

That makes it much closer to a real Agent RL system than a synchronous PPO/GRPO loop with tool calls.

---

## 2. The Main Difference vs `train_agent.py`

### 2.1 Synchronous baseline: `train_agent.py`

`train_agent.py` follows the standard online RL rhythm:

```text
rollout batch -> reward -> policy update -> sync rollout policy -> next batch
```

Properties:

- a full rollout batch is completed before every update
- rollouts are mostly generated by the same policy snapshot
- the logic is easy to follow and debug
- but the learner often waits for rollout

### 2.2 Asynchronous pipeline: `train_agentic_rl_async.py`

The async trainer introduces an `AsyncRolloutManager`:

- multiple producer threads keep sampling prompts
- background workers keep expanding multi-turn trajectories
- trajectories are pushed into a queue
- the learner consumes sufficiently fresh groups without strict step-by-step lockstep

Immediate benefits:

- less learner idle time
- better rollout utilization
- a cleaner trainer / rollout split
- a much more realistic Agent RL execution model

## 3. What the Async Trainer Actually Adds

This is not just "the synchronous script plus threads". It adds the missing mechanics that async RL really needs.

### 3.1 Policy version tracking

Each trajectory and each token carries policy-version metadata:

- `PolicyVersion`
- `response_versions`
- `per_token_versions`
- `group.policy_version`

This lets the learner know:

- which behavior policy produced the data
- how stale that data is relative to the current policy

That is the foundation for any stable asynchronous PPO-style update.

### 3.2 Staleness control instead of blindly consuming the queue

The central async problem is not thread safety. It is **off-policy drift**.

This script controls it with three layers:

- `max_version_gap`: groups that are too old are dropped
- `resolve_prox_logps(...)`: behavior logprobs are corrected toward a proximal policy
- `async_stale_discount`: older trajectories receive lower loss weight

So the system does not simply trust stale data, and it also does not throw everything away. It trades throughput against policy freshness explicitly.

### 3.3 Trainer-rollout split

The script supports:

- `multi_gpu_mode=ddp`
- `multi_gpu_mode=trainer_rollout`

`trainer_rollout` is the more system-like mode:

- one rank is primarily responsible for learning
- the remaining ranks focus more on rollout production
- prefetch, group fetch, and queueing connect the two sides

That is a better fit for tool-use agents, where rollout is often heavier than the update itself.

### 3.4 Async-specific observability

A synchronous script mostly needs reward, KL, and entropy.

This trainer also logs:

- `async/staleness_group_mean`
- `async/staleness_group_max`
- `async/token_staleness_*`
- `async/row_weight_mean`
- `async/queue_utilization`
- `async/avg_rollout_sec`
- `async/avg_train_wait_sec`
- `async/train_wait_sec_p90`
- `async/online_group_accept_rate`
- `async/stale_drop_rate`

That matters because an async run cannot be judged by reward alone. You also need to know:

- whether the queue stays empty
- whether the learner keeps waiting for rollout
- whether stale samples are accumulating
- whether rollout throughput matches training throughput



## 4. Training Flow

```text
Prompt Pool
   -> AsyncRolloutManager
   -> rollout workers / rollout ranks
   -> trajectory queue
   -> pack_groups
   -> compute_async_loss
   -> optimizer step
   -> policy sync
   -> next fresh trajectories
```

At the highest level:

```text
sample prompt
-> multi-turn tool rollout
-> delayed reward on the full trajectory
-> stale-aware PPO-style update
-> periodic rollout-policy sync
```

### 5.2 How to interpret the results

If async training is healthy, you usually want to see:

- reward rising instead of stalling early
- exact match and answer coverage improving alongside reward
- tool success and tool value coverage improving together
- queue utilization staying meaningfully above zero
- train wait not dominating rollout time
- staleness staying controlled rather than growing without bound

The point of async optimization is not just "faster". It is:

- to reduce learner idle time
- while preserving stable policy updates

## 6. Default Training Bias

The default configuration is clearly aimed at **stabilizing small-model math tool-use agents first**.

Defaults include:

- data: `dataset/agent_rl_math.jsonl`
- tool subset: `calculate_math,unit_converter,get_current_time`
- `num_generations=4`
- `max_turns=3`
- `max_gen_len=192`
- `use_decoupled_ppo=1`
- `beta_auto_tune=1`
- a non-zero BC auxiliary term

This is not primarily a general-agent benchmark preset. It is a practical setup to teach a small MiniMind policy to:

- decide whether a tool is needed
- choose the right tool
- incorporate tool outputs into the final answer

## 7. Quick Start

### 7.1 Torch rollout

```bash
torchrun --nproc_per_node=4 trainer/train_agentic_rl_async.py --rollout_engine torch
```

or

```bash
python trainer/train_agentic_rl_async.py --rollout_engine torch
```

### 7.2 SGLang rollout

Start the server first:

```bash
python -m sglang.launch_server --model-path ./minimind-3 --attention-backend triton --host 0.0.0.0 --port 8998
```

Then train:

```bash
python trainer/train_agentic_rl_async.py \
  --rollout_engine sglang \
  --sglang_base_url http://localhost:8998 \
  --sglang_shared_path ./sglang_ckpt_agentic_async
```

### 7.3 If you want to understand the evolution

Read the code in this order:

1. `trainer/train_agent.py`
2. `trainer/train_agent_async.py`
3. `trainer/train_agentic_rl_async.py`

That makes the progression much easier to see:

- synchronous Agentic RL
- then local async queuing
- then a version-aware trainer-rollout async system
